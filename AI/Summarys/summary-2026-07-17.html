Resumen

PWA fitness integral con rutinas inteligentes, nutricion personalizada, tracking al milimetro y gamificacion completa. Construida con React 19 + TypeScript + Vite en el frontend (client/) y ASP.NET Core 10 + EF Core + PostgreSQL + Redis en el backend (server/AegiFitness.Api/). Orquestada via Docker Compose con 5 servicios: base de datos, cache, API, Nginx para la PWA y tunel Cloudflare.

Un solo despliegue. Una sola UI adaptable (sidebar en escritorio, bottom-nav en movil). Vistas unicas role-gated: Admin y Member conviven en las mismas rutas sin duplicacion de pantallas. 185 ejercicios y 140 comidas sembrados en catalogo. Motor de rutinas semanales con 6 modos de entrenamiento. Motor de planes de comida por objetivo con rotacion determinista. 12+ logros, niveles con titulos, rachas y metas auto-evaluadas.

Bugs corregidos durante verificacion (10)
  • Esquemas de autenticacion pisados por AddIdentity — AddIdentity sobrescribia DefaultAuthenticateScheme y DefaultChallengeScheme. Fix: fijar los tres esquemas a JwtBearerDefaults.AuthenticationScheme.
  • MapInboundClaims=false rompia busqueda de sub — El mapeo entrante convertia "sub" a NameIdentifier. Fix: usar FindFirst("sub") explicitamente en validacion de token.
  • DbUpdateConcurrencyException en entidades hijas — Asignar entidades nuevas a navigation properties de un padre ya trackeado causaba concurrencia. Fix: usar AddRange explicito en vez de navegacion.
  • Cache de licencia no invalidada — Al aprobar, suspender o revocar, el cache Redis de /me devolvia estado anterior. Fix: invalidar entrada de cache tras cambios de licencia.
  • NullReferenceException en MetricsService — ThenInclude faltante para Exercise en WorkoutLogEntry causaba NRE al calcular volumen por musculo. Fix: agregar .ThenInclude(e => e.Exercise) en la query.
  • Redirect fantasma a /login al visitar /register sin sesion — El evento aegi:logout se disparaba incluso sin sesion activa. Fix: disparar evento solo si habia sesion previamente.
  • Keys duplicadas en grafico de barras — Labels de semana repetidos cuando la query devolvia multiples filas para el mismo dia. Fix: agregar DistinctBy fecha en la agregacion del dashboard.
  • Garantia 50/50 en dias Both — La seleccion de ejercicios Gym vs Calistenia no aseguraba proporcion equitativa. Fix: algoritmo de mezcla con minimo 2 de cada tipo si hay >=5 ejercicios.
  • Foco del plan en espanol — El campo Focus del plan de entrenamiento se generaba en ingles. Fix: mapear nombres de musculos y modos al espanol.
  • CacheService sin resiliencia a caida de Redis — Si Redis no respondia, la API lanzaba excepcion en vez de degradar graceful. Fix: try-catch con fallback a IMemoryCache y reintento diferido.

Bugs corregidos en esta iteracion (5)
  • Npgsql rechazaba DateTime Kind=Unspecified en timestamptz — 500 al poner vencimiento de licencia o deadline de meta porque EF enviaba DateTime con Kind=Unspecified. Fix: DateTime.SpecifyKind(value, DateTimeKind.Utc) antes de persistir todo timestamptz.
  • NRE al mapear plan recien generado en /workout-plans/regenerate — La respuesta del endpoint devolvia entidades sin includes; navigation properties nulas causaban NRE en el mapper. Fix: re-query del plan recien creado con .Include() y .ThenInclude() completos antes de mapear.
  • Ejercicios duplicados por nombre en el plan — Variantes Bulk/Cut del catalogo compartian nombre pero tenian IDs distintos; el generador seleccionaba ambas. Fix: deduplicacion por nombre en el generador, manteniendo la variante mas adecuada al objetivo.
  • Metas WeeklyWorkouts y rachas en 0 — Anclas UTC del servidor vs dia local del usuario hacian que entrenos de tarde/noche no contaran para la meta/racha. Fix: anclas por fecha de actividad del usuario (local) en vez de UTC del servidor.
  • E2E con procesos huerfanos y networkidle eterno — Playwright se colgaba esperando networkidle; procesos del navegador quedaban huerfanos entre corridas. Fix: watchdog de 3 min, kills por arbol de procesos, waitUntil domcontentloaded en vez de networkidle. Ahora 32s.
Despliegue

Pasos para poner en produccion en cualquier servidor con Docker:

# 1. Clonar y configurar entorno cp .env.example .env # Editar .env: POSTGRES_PASSWORD, JWT_KEY (min 32 chars), SEED_ADMIN_PASSWORD # 2. Levantar stack completo (db, redis, api, web) docker compose up -d --build # 3. Tunel Cloudflare (opcional, perfil tunnel) docker compose --profile tunnel up -d # 4. Acceder # PWA: http://servidor:8080 # Admin seed: usuario "admin", password = SEED_ADMIN_PASSWORD

El admin seed (usuario 1) nace con licencia Active y rol Admin. Los demas usuarios se registran solos, quedan en estado Pending y solo pueden usar la app tras ser aprobados desde Admin → Usuarios. Nginx sirve la PWA y proxifica /api al backend.
